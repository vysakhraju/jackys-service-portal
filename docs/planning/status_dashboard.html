What the pre-mortem caught before it shipped

  • 01
    No GET /invoicing list-all endpoint existed — only by-id, by-job-card, and the B2B aging report (unpaid B2B only).

    A naive "Invoices" tab built from the aging response alone would have structurally hidden every B2C invoice and every paid/cancelled one from Finance staff — a real money-tracking gap, not a UI inconvenience. Fixed with a small new GET /invoicing endpoint (optional status/customerType filters), same class of addition as Phase 8's own GET /delivery/:id/job-cards.

  • 02
    Customer Portal route shape — three backend endpoints, but all keyed off one shared publicToken.

    Three separate URLs would only ever mean deciding which one link to send a customer and orphaning the other two. Resolved as one page, /track/:token, with three sections — Status eager-loads for the header, "What You Owe" and "Download Summary" fetch lazily only once their tab is opened.

  • 03
    Delivery's role-gating pattern is a page-level self-check that still lets the page (and its queries) mount for anyone.

    Finance data is more sensitive, so it's gated at the layout level instead — the same pattern PermissionsPage (Phase 7) uses. A non-privileged user's child route never mounts, so no invoicing query is ever even constructed for them, not just rejected server-side.

  • 04
    A customer looking at "amount due" with no pay button is a predictable support complaint waiting to happen.

    FR-14 is manual-payment-only — no online gateway. The invoice section leads with the amount, then an explicit, unmissable line on how to actually pay, never left implicit.

What the pre-mortem caught before it shipped

  • 01
    A token captured once at mount goes stale after the 15-minute access-token lifetime, and Socket.io does not auto-reconnect after a server-initiated disconnect.

    Fixed: useReportsSocket.ts passes a function-form auth option (io(url, { auth: cb => cb({token}) })) that reads the token fresh on every (re)connection attempt, and on an "io server disconnect" event proactively calls GET /auth/profile — piggybacking on api.ts's existing silent-refresh interceptor — before manually calling socket.connect() again.

  • 02
    A dropped live connection can look exactly like a quiet moment with nothing to report.

    Fixed: a ConnectionPill always visibly renders connecting/live/reconnecting/offline, escalating to offline only after 5 consecutive connect_error events so ordinary transient retries don't false-alarm.

  • 03
    The backend's own poll-and-diff design means "live" can lag up to 5 seconds by design — presenting it as instant risks false urgency or false calm.

    Fixed: a shared formatAsOf() helper renders the backend's own asOf timestamp on every card, so current vs. a few seconds behind vs. point-in-time report is always legible, never implied.

  • 04
    Service Efficiency and First-Time Fix Rate are never pushed by the gateway — blending them into the live feed would read as a bug, not a design choice.

    Fixed: both get their own useQuery calls, their own manual Refresh button, and their own captured-at-fetch asOf, visually tagged "Report" against the "Live" tag on the Kanban/Approval Aging cards.

  • 05
    REPORTS_VIEW_ROLES is unusually narrow (no ACCOUNTANT/FINANCE_MANAGER, unlike every other module) — a restricted role must never even attempt the WebSocket handshake.

    Fixed: canViewReports() runs first in ReportsPage, gating both the REST queries (enabled: canView) and useReportsSocket(canView) before any network or WS attempt.
