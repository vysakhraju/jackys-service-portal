What the pre-mortem caught before it shipped

  • 01
    No backend endpoint returned "which job cards are in delivery X" — only the reverse (job-card → its delivery) existed.

    Fixed with a small, safe backend addition: GET /delivery/:id/job-cards, a thin wrapper over the already-existing (previously internal-only) JobCardsService.findByDeliveryId — same class of small defensive fix as the Phase 7 pre-mortem's JobCardsService.cancel() guard extension.

  • 02
    An eager per-row invoice lookup on the Ready tab would silently mint DRAFT invoices for jobs nobody had decided to deliver yet.

    Fixed: the Ready tab uses the invoiceStatus/payable fields GET /delivery/ready already returns (a genuinely side-effect-free lookup) — the lazy-create endpoint is only called on an explicit user action, never just by rendering a list.

  • 03
    The Delivery 409-blockers shape names job cards + invoices, not spare-part reservations like Phase 6/7's — QcPage's renderer wouldn't fit.

    Fixed: a dedicated DeliveryBlockersNotice component, shared between the Ready tab's batch-create 409 and the Deliveries tab's defensive POD-time re-check 409, each with its own "Record payment" action per blocked row.

  • 04
    POD capture (signature/photo, AC-12) has no camera or signature-pad component anywhere in this app.

    Shipped as plain file uploads read client-side into a base64 data URI — works, flagged as a known UX gap for later rather than pulling in a new dependency for one field.
