What the pre-mortem caught before it shipped

  • 01
    No backend endpoint returned "which job cards are in delivery X" — only the reverse (job-card → its delivery) existed.

    Fixed with a small, safe backend addition: GET /delivery/:id/job-cards, a thin wrapper over the already-existing (previously internal-only) JobCardsService.findByDeliveryId — same class of small defensive fix as the Phase 7 pre-mortem's JobCardsService.cancel() guard extension.

  • 02
    An eager per-row invoice lookup on the Ready tab would silently mint DRAFT invoices for jobs nobody had decided to deliver yet.

    Fixed: the Ready tab uses the invoiceStatus/payable fields GET /delivery/ready already returns (a genuinely side-effect-free lookup) — the lazy-create endpoint is only called on an explicit user action, never just by rendering a list.

  • 03
    The Delivery 409-blockers shape names job cards + invoices, not spare-part reservations like Phase 6/7's — QcPage's renderer wouldn't fit.

    Fixed: a dedicated DeliveryBlockersNotice component, shared between the Ready tab's batch-create 409 and the Deliveries tab's defensive POD-time re-check 409, each with its own "Record payment" action per blocked row.

  • 04
    POD capture (signature/photo, AC-12) has no camera or signature-pad component anywhere in this app.

    Shipped as plain file uploads read client-side into a base64 data URI — works, flagged as a known UX gap for later rather than pulling in a new dependency for one field.

What the pre-mortem caught before it shipped

  • 01
    No GET /invoicing list-all endpoint existed — only by-id, by-job-card, and the B2B aging report (unpaid B2B only).

    A naive "Invoices" tab built from the aging response alone would have structurally hidden every B2C invoice and every paid/cancelled one from Finance staff — a real money-tracking gap, not a UI inconvenience. Fixed with a small new GET /invoicing endpoint (optional status/customerType filters), same class of addition as Phase 8's own GET /delivery/:id/job-cards.

  • 02
    Customer Portal route shape — three backend endpoints, but all keyed off one shared publicToken.

    Three separate URLs would only ever mean deciding which one link to send a customer and orphaning the other two. Resolved as one page, /track/:token, with three sections — Status eager-loads for the header, "What You Owe" and "Download Summary" fetch lazily only once their tab is opened.

  • 03
    Delivery's role-gating pattern is a page-level self-check that still lets the page (and its queries) mount for anyone.

    Finance data is more sensitive, so it's gated at the layout level instead — the same pattern PermissionsPage (Phase 7) uses. A non-privileged user's child route never mounts, so no invoicing query is ever even constructed for them, not just rejected server-side.

  • 04
    A customer looking at "amount due" with no pay button is a predictable support complaint waiting to happen.

    FR-14 is manual-payment-only — no online gateway. The invoice section leads with the amount, then an explicit, unmissable line on how to actually pay, never left implicit.

What the pre-mortem caught before it shipped

  • 01
    The generic PUT /appointments/:id/complete used to be reachable for an AMC-type PM visit too, silently losing its checklist/signature/extra-charge record forever.

    Fixed at the source: appointments.service.ts now rejects any AMC-type appointment on that endpoint outright (it's directly callable via Swagger/curl, so a UI-only fix wasn't enough). SchedulePage.tsx's row action for an AMC row is now "Complete PM Visit →", linking into the AMC module's own completion flow instead.

  • 02
    Four different, overlapping role arrays living in one component was flagged as a likely copy-paste-wrong-array bug source.

    Centralized into a single amcPermissions(roleName) helper computing {canView, canManage, canCompleteVisits, canBill} once, used everywhere instead of inline .includes() checks — tested exhaustively across every role combination.

  • 03
    Billing invoice periodLabel is caller-supplied free text with nothing else tying an invoice to "the period it covers" — a double-click or a re-bill months later could silently generate a duplicate.

    Fixed: generateBillingInvoice() now rejects a duplicate non-cancelled periodLabel on the same contract, with regression tests confirming a genuinely different period is still allowed.

  • 04
    Expiring Soon and Upsell Candidates risked being pure read-only dead ends with no next action.

    Fixed: each Expiring row gets an in-row "Send reminder" action plus a link into the full contract; each Upsell row links straight into a pre-filled Create Contract form.

  • 05
    The backend's 60-visit safety cap had no client-side preview — a long form could be filled out entirely only to 400 on submit.

    Fixed: a client-side estimateVisitCount() mirrors the backend's own date math exactly, shown live on Create/Renew, disabling submit once the estimate exceeds the cap.

What the pre-mortem caught before it shipped

  • 01
    A BOM-code typo at harvest time silently and permanently drops a component's eligibility, with no re-harvest path once the record moves on.

    Fixed: HarvestModal.tsx's BOM item code field is wired to a datalist sourced from the model's existing Component Yield Matrix, with a live inline warning under any line whose code doesn't match. The harvested-components table also flags a no-match component with a distinct "⚠ not in yield matrix" badge instead of blending it in with a genuine CONSUMABLE/SCRAP row.

  • 02
    Price-and-post is the only pricing pass a record ever gets — under-selecting looks recoverable but is actually permanent forfeiture.

    Fixed: PriceAndPostModal.tsx shows an always-visible "this is the only pricing pass this record will ever get" banner, and a strict-subset selection requires an explicit "I understand the rest will be permanently forfeited" checkbox before submit enables.

  • 03
    A mid-submit 409 Conflict (two eligible people racing the same record) could silently discard a manager's typed-in prices.

    Fixed: the mutation's onError branch shows a distinct "reload and retry" message for a 409 specifically, and never calls reset() on any error path — entered prices survive the race.

  • 04
    Client-side pre-emptive gating of Verify/Price & Post could create false confidence if it's ever wrong.

    Kept deliberately as a UX hint layered on the backend's real enforcement, not a replacement for it: canVerifyAsUser()/canPriceAsUser() mirror the backend's exact same-person checks to pre-emptively disable the buttons with an inline AC-31 explanation.

  • 05
    Four overlapping role arrays (HARVEST/VERIFY/MANAGER/VIEW) — the same fragmentation risk the-fool flagged for AMC in Phase 10.

    Fixed the same way: collapsed into a single dismantlingPermissions(roleName) helper from the start, tested exhaustively across representative roles.
