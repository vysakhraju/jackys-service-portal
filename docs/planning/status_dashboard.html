Then, live, on the very first aggregate() call: it and recordCreditNote() both re-fetched their own just-written row through the @InjectRepository()-injected repository — a different DB connection than the surrounding transaction's own queryRunner — so the read couldn't see the write yet. aggregate() 404'd outright; recordCreditNote() would have silently returned stale data. Fixed by re-fetching through the transaction's own manager in aggregate(), and by dropping the unnecessary transaction from recordCreditNote() entirely, matching DismantlingService.priceAndPost()'s established "GL posting sequenced after the persisting write, not nested inside it" pattern. Mobile Phase 4 (2026-09-04): Offline queue layer

Built right after Phase 3's live verification, per the scope doc's phased order — "offline queue layer, retrofitted onto the actions from Phases 2-3". Before building, resolved the one still-open design question from the pre-mortem (§9 finding #3) via AskUserQuestion: what should happen when a queued item fails to replay for a reason unrelated to reassignment (e.g. the appointment was cancelled while offline)? Extra Role Access (2026-09-03): admin can delegate a role's access to any user

A second, complementary admin capability on top of User Management: an admin can now temporarily hand a user everything a different role can do, on top of their own real role — the vacation-cover case ("the Team Leader is out, let a capable CCE cover TL-level approvals for two weeks") — without ever changing that user's actual role, login, or identity. Built as one additive fallback check inside RolesGuard, the single guard nearly every controller already uses, so it reaches every module through one reviewed change rather than a per-controller retrofit. the-fool pre-mortem ran first (mode: Find failure modes) given this is now the highest-leverage file in the backend; all 5 findings are in the shipped design: Super Admin, Service Head, and Customer can never be delegated (would recursively hand out the entire admin surface, including this grant screen itself); an admin can never grant access to their own account (403, same self-lockout precedent as User Management); every grant is time-boxed with a mandatory expiry, capped at 90 days — there is no standing/permanent grant; the guard fails closed — any lookup error denies access rather than silently allowing it; and the QC approve/reject gate (Section 12a) stays a separate sign-off — the live capability preview flags those two endpoints explicitly so an admin never assumes delegating TL access alone unlocks QC approval too.

The admin-facing preview itself is auto-generated, not hand-maintained: it walks every registered controller's real route metadata at request time (NestJS's own DiscoveryService / MetadataScanner) so "what will this user be able to do" is always the actual live routes, never a list that can drift out of date.
